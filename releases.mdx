title: "Releases and Versioning"
description: "How Mushroom Pi versions its components, what a release is, and where the single canonical changelog lives."

Mushroom Pi versions each component independently, and **GitHub Releases is its single canonical changelog**. This page explains what the version numbers mean and where to find the per-release record. It is written once and does not change from release to release — there are no per-release notes, release summaries, or "latest version" pointers hosted on this site.

## Each component carries its own version

Every shipping component — the Pico firmware (`mushpi-grow`), the server (`mushpi-server`), the dashboard (`mushpi-client`), the mock unit (`mushpi-mock`), and the hub bundle (`mushpi-hub`) — carries **its own SemVer version**, `MAJOR.MINOR.PATCH`, bumped when that component changes. There is no single suite version the five must all equal: a component that did not change keeps its previous version and tag.

A release is one number — recorded in `mushpi-hub/release.json` and tagged `vX.Y.Z` — that **names** the versions it ships rather than imposing a shared number. When a release is cut, only the components that changed move; the rest are carried forward unchanged.

The mock unit carries **two version identities**. Its **own release version** — `mushpi-mock`'s `pyproject.toml` and `VERSION` — tracks its packaging and image tag, and its **simulated firmware version** — `state.py::_SOFTWARE_VERSION` — always equals the real `mushpi-grow` firmware version. The two are independent: the mock's own version **may lead the firmware version it simulates**, so a mock release can ship a tool change while the firmware stands still. The hub's verify script asserts each against its own source — `firmware` against grow's `_SOFTWARE_VERSION` and `mock` against the mock's `VERSION` — never against each other.

Every version string is a strict `MAJOR.MINOR.PATCH` — no pre-release suffixes (`-rc`) and no build metadata (`+build`).

## `api_version` is not a release number

Separate from the component versions is **`api_version`** — a plain integer marking the generation of the Pico↔Server REST contract. It is bumped only when that contract breaks (an endpoint removed or renamed, an incompatible request or response shape), never for additive changes or bug fixes, and never merely because a release is cut.

The server reads the `api_version` a unit reports and **judges** it against its supported range, flagging the unit `compatible`, `incompatible`, or `unknown`. It flags an out-of-range value — it never rejects the unit. `api_version` is a contract generation, not a release and not a version of anything.

## What a release is

A release is a **`v*` git tag** in the release repository (`mushpi-hub`) — for example `v0.9.0` — paired with the `release.json` manifest that records the release number alongside the version of each shipped component. The single canonical per-release record is the **GitHub Release** attached to that tag: what changed, what to test, and any upgrade notes.

## The changelog lives on GitHub

The docs you are reading deliberately do **not** host a changelog. Per-release notes and release summaries all live in the GitHub Releases index, which is always current:

**[https://github.com/mushroom-pi/mushpi-hub/releases](https://github.com/mushroom-pi/mushpi-hub/releases)**

Always link to the **index**, never to a specific tag, so the pointer stays valid whether a release is ahead, deleted, or not yet cut.
