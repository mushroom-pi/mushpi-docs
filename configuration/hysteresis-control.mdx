Each Pico unit runs its own **control loop** — a small program on the unit itself that reads the DHT11 sensor and switches three relays (the humidifier, the fan and the heater) to hold temperature and humidity near the targets you set. It re-evaluates everything every `period_s` seconds (default **10**), on the unit, independently of anything the server does.

The loop is **asymmetric**: it does not use one even band around each target. Humidity has two different edges, temperature has one, and every relay has a minimum runtime. That is the whole model, and it matters because it changes how you read the unit's behaviour.

## How humidity is controlled

Two devices act on humidity, one on each side of the target, and they are mutually exclusive — the loop never runs both at once.

| Device | Switches on when | Switches off when |
|---|---|---|
| **Humidifier** | humidity ≤ target − `humidity_deadband` (default **3**) | humidity rises back above that threshold, once the minimum runtime has elapsed |
| **Fan** | humidity > target + `hyst_hum` (default **5**) | humidity drops back to ≤ target + `hyst_hum` |

The humidifier adds moisture, so it runs when humidity is too low. The fan removes moisture, so it runs when humidity is too high. Between `target − humidity_deadband` and `target + hyst_hum` neither runs — this dead zone is what stops the two devices fighting each other, and it is deliberately wider on the high side (`hyst_hum`, default 5) than the low side (`humidity_deadband`, default 3).

There is no "humidifier off above the upper threshold". Once humidity is above the target, pushing it back down is the fan's job, and the humidifier is already off.

## How temperature is controlled

Only the **heater** acts on temperature, and it can only add heat. There is no cooling device on the unit, so nothing pulls temperature down — only the environment does.

| Device | Switches on when | Switches off when |
|---|---|---|
| **Heater** | temperature ≤ target − `temperature_deadband` (default **1**) | temperature rises above that threshold, once the minimum runtime has elapsed |

This means temperature is held from below: the heater keeps it from falling below the target, and any rise above the target is left to cool on its own.

## Minimum runtime

To stop a relay from chattering when the reading hovers around an edge, any relay that switches on must stay on for at least `min_runtime` seconds (default **30**). A relay that is already on will not switch off until it has run that long, even if the reading has already crossed back.

## The loop's rhythm

The loop evaluates all of this on its own clock — every `period_s` seconds (default **10**) — on the unit, not on the server. This is separate from the server's one-minute poll, which is only how readings and status are read back.

## Sensor faults are not fail-safe

The loop needs a plausible reading to act on, and the DHT11 can return garbage or nothing at all. When it does, the unit does **not** fail safe. The first plausible reading is stored; after that, a failed read leaves the previous value in place, and the loop carries on using it. In other words, if the sensor stops working — or starts reporting nonsense — the relays can keep switching on the strength of a number that is now stale. The unit records the fault in `last_sensor_error`, but that is a flag, not a stop: it does not turn the relays off. A grower needs to know this, because a broken sensor does not necessarily stop the environment control — it can keep it running on old data.

## Targets are whole numbers

Temperature and humidity targets are integers, and the loop compares the reading against them as such.

## Where the settings live

Everything that tunes the loop — `hyst_hum`, `humidity_deadband`, `temperature_deadband`, `min_runtime` and `period_s` — is set in the unit's `config.json`, on the unit itself. None of it is exposed in the dashboard, and none of it is a recipe or batch field: a recipe carries the temperature and humidity **targets**, not the hysteresis.

The two things you *can* change from the dashboard are the **targets** and the **control-loop on/off toggle**, on a unit's own page — see [Your units](/dashboard/pico-units).

## How changes reach the unit

When you change a unit's targets or toggle the loop in the dashboard, the server **pushes** that change to the unit immediately through its control routes. The 60-second poll is the other direction: the unit's sensor readings and relay status come back to the server on that schedule. The server does not wait for the next poll to deliver a setpoint change.
