Mushroom Pi exposes two REST APIs, and the reference pages in this section are **generated directly from their OpenAPI specifications** — every endpoint, parameter, schema and response documented here comes from the committed spec, so it matches what the code serves.

- **Mushpi Server API** — the Raspberry Pi hub (`mushpi-server`, NestJS). Units, readings, batches, recipes, control proxies, dashboard summary and settings. Canonical spec: `spec/openapi.json` in the `mushpi-server` repository.
- **Pico REST API** — every Pico 2W unit (`mushpi-grow`, MicroPython). Sensors, setpoints, outputs, wiring setup, manual control and provisioning. The hub polls each unit on this API every 60 seconds. Canonical spec: `spec/openapi.yaml` in the `mushpi-grow` repository.

## Base URLs

| API | Base URL |
|---|---|
| Server (hub) | `http://<your-pi-ip>:3000` |
| Pico unit | `http://<pico-ip>:5000` |

Replace the placeholders with the device's local IP address or hostname. All request and response bodies use JSON.

## Versioning

The server API is URI-versioned: all functional endpoints live under `/v1/` (for example `/v1/pico-units`). Only the infrastructure probes `GET /ping` and `GET /health` sit outside the version prefix. The Pico API is unversioned.

## Authentication

Neither API requires authentication by default — what protection exists depends on your deployment:

- **Server — optional app secret.** If the server runs with `APP_SECRET` configured, every request must carry `Authorization: Bearer <APP_SECRET>`; requests without it (or with the wrong value) are rejected with `426 Upgrade Required`. The server specification declares this as its `secret` bearer scheme. Without `APP_SECRET`, no bearer check is made.
- **Server — announce secret.** `POST /v1/pico-units/announce` is a hardware-facing route: Pico units present themselves with a shared secret in the `X-Pico-Secret` header (`PICO_ANNOUNCE_SECRET` on the server, matching each unit's `hub_secret`). See [environment variables](/deployment/environment). Browser and script callers never need this header.
- **Pico units — none.** The firmware API deliberately implements no authentication. Access control is network-level: keep port 5000 inside your LAN and never expose it through your router or firewall.

## CORS

The server enables CORS with credentials for the origins it knows: the dashboard (`CLIENT_URL`) and, when enabled, its own docs UI. Browser applications on other origins will be blocked; server-side scripts and `curl` are unaffected. The Pico API is meant for local-network callers and applies no CORS rules.

## Interactive docs

When the server's docs endpoint is enabled (`DOCS_ENDPOINT`), it serves the machine-readable OpenAPI document at `/<DOCS_ENDPOINT>-json` together with an interactive UI. The docs variables — like every environment variable mentioned here — are listed in [environment variables](/deployment/environment).

<Note>
  Direct calls to a Pico unit bypass the backend and are subject to the unit's local hysteresis control loop, which may reverse a manual relay change at its next evaluation. See [hysteresis control](/configuration/hysteresis-control).
</Note>
