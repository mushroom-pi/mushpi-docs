The grow-unit firmware lives in the [mushpi-grow](https://github.com/mushroom-pi/mushpi-grow) repository. It is MicroPython, serving a lightweight REST API on **port 5000** with [Microdot](https://github.com/miguelgrinberg/microdot) — the same API the hub polls every 60 seconds for readings and relay commands.

**Prerequisites:** Python 3.8+ on your computer, the **MicroPico** VSCode extension (`paulober.pico-w-go`) or [Thonny IDE](https://thonny.org), a data-capable micro-USB cable, and the unit wired as described in [Wiring](/pico-units/wiring).

## What is on the device

After you deploy, the Pico's flash holds this layout:

```
/                         # flash root
├── main.py               # entry point — the boot sequence
├── config.json           # Wi-Fi, hub URL, device name, pins, control (gitignored)
├── runtime.json          # your saved settings — targets, loop switch, hand-set fan/humidifier (written by the unit as you change them)
├── app/                  # firmware modules (state, control, api, wifi, …)
│   └── provision.html    # the AP provisioning form
└── lib/                  # third-party libraries (not tracked in git)
    └── microdot.py
```

## 1. Flash MicroPython

Download the **Raspberry Pi Pico 2W** UF2 image from [micropython.org/download/RPI_PICO2_W](https://micropython.org/download/RPI_PICO2_W/). **v1.26.0 or newer** is the recommended minimum (see [mDNS caveats](#mdns-caveats)).

1. Hold **BOOTSEL**.
2. Connect the Pico to your computer via USB while holding it.
3. Release BOOTSEL — the Pico mounts as a USB drive called **RPI-RP2**.
4. Drag the `.uf2` file onto **RPI-RP2**.

The Pico reboots into MicroPython; the drive disappears and the Pico re-enumerates as a serial device.

## 2. Get the firmware and its libraries

Clone the repository:

```bash
git clone https://github.com/mushroom-pi/mushpi-grow.git
cd mushpi-grow
```

The firmware needs exactly one third-party library on the device in `lib/`: `microdot.py`. It is **not tracked in the repo**, so install it one of two ways:

- **With `mip`** (MicroPython's package manager), from a REPL:

  ```python
  >>> import mip
  >>> mip.install("microdot")
  ```

- **Manually** — download the single file into the device's `lib/` folder, as the [grow README](https://github.com/mushroom-pi/mushpi-grow) describes.

All firmware HTTP — the announce and the responses to the hub's polls — speaks the standard `usocket` stack, so no HTTP-client library is needed. A leftover `lib/urequests.py` from an earlier flash is harmless and can be left in place.

## 3. Configure `config.json`

`config.json` is gitignored, so create it at the repo root if it is not already present. Its real keys:

| Key | What it sets |
|---|---|
| `wifi.ssid` / `wifi.password` | Your Wi-Fi network name and password |
| `wifi.networks` | Optional fallback networks, tried in order |
| `hub_url` | The hub's address only (scheme, host, port) — e.g. `http://<hub-name>.local:3000`. The firmware appends the registration path itself; older values that still include the full path keep working. The unit resolves the hub's name **once, at boot** — if you change the hub's address (or its name stops resolving), the unit picks up the change at its next boot, not while it is running. A recent MicroPython is needed on the unit for name resolution to work — see [mDNS caveats](#mdns-caveats). |
| `hub_secret` | Must match the hub's `PICO_ANNOUNCE_SECRET` |
| `device_name` | The unit's name — becomes its `handle` on the hub |
| `api_port` | The REST API port (default `5000`) |
| `control` | Hysteresis and control-loop parameters (period, deadbands, minimum runtime) |
| `reboot` | Optional daily scheduled reboot (disabled by default) |
| `pins` | GPIO map — defaults `dht` 4, `humidifier` 6, `fan` 7, `heater` 8 |
| `active_high` | Relay polarity — `false` (default) for active-low modules |

Notice what is **not** in `config.json`: your **temperature and humidity targets** and the **control-loop on/off** state. Those are your choices, not provisioning, so the unit saves them separately and restores them at boot — see [What survives a restart](#what-survives-a-restart). Re-flashing `config.json` never touches them.

Make the GPIO values match your physical wiring (see [Wiring](/pico-units/wiring)). If you would rather not edit `config.json` at all, the unit can be provisioned through its access-point setup flow instead — see [Offline operation](/pico-units/offline-operation).

## 4. Deploy the files

With the Pico connected via USB and MicroPython flashed, deploy the firmware with the **MicroPico** VSCode extension: it uploads every `.py` file, `app/provision.html`, and `config.json` to the flash. Thonny's file manager (File → Save as… → MicroPython device) also works. Make sure the library from step 2 landed in `lib/`.

## 5. Reboot and watch it start

Press **Ctrl-D** in a serial console (Thonny or MicroPico), or unplug and reconnect the USB cable. `main.py` runs on boot, and the unit:

1. Connects to your Wi-Fi network (the onboard LED stays off until it does).
2. Announces itself to the hub address in `hub_url`. The announce is a background task spawned once at boot that runs alongside the control loop and REST API below: the hub address is resolved once on the boot path, before the watchdog is armed, and each attempt is bounded — about a 3-second connect ceiling, then about 6 seconds of response-waiting in 1-second slices that yield to the control loop. A failure to resolve or get a response is logged — it does not reset the unit, which keeps regulating and serving its REST API while the announce retries forever in the background, backing off 30 s → 30 s → 60 s → 120 s → 300 s (capped at 300 s), until the hub accepts it.
3. Runs the control loop — reading the sensor and driving the relays every `control.period_s` seconds (default 10) — and serves the REST API on port 5000. The hub then polls it every 60 seconds.

Once announced, the unit appears on the hub automatically; you can also register it manually through the dashboard. The unit also serves its own status-and-control page — the same view it exposes to the hub's poll, in a browser — at `http://<device_name>.local:5000/`, with no hub required; `GET /ui` is an alias for the same page. See [The unit's own page](/pico-units/unit-page).

## Recovery and resilience

The firmware is designed to self-heal without human intervention:

- **Wi-Fi reconnect backoff.** A watchdog monitors the link every 5 seconds. On a drop it reconnects with increasing delays — 5 s → 10 s → 30 s → 60 s, then staying at 60 s until the link returns — trying each configured network in order. Relay control continues throughout the outage; only the connection is affected. A Wi-Fi link bounce does not trigger a re-announce: the background announce task carries the unit's new IP on its next retry, and the regular 60-second poll also refreshes the stored IP on every successful poll — so an already-known unit recovers without any announce.
- **Watchdog timer.** A hardware watchdog reboots the Pico if the control loop freezes for more than 8 seconds. It is armed at boot, before the control-loop, announce and Wi-Fi tasks are created; the hub address is resolved before it is armed — once, on the boot path, and never again at runtime. An unreachable hub, or one whose network name will not resolve, can therefore never cause a reset and never stops regulation: the unit keeps controlling humidity and temperature and keeps serving its REST API, while the announce keeps retrying in the background rather than resolving — a hub whose address changes is picked up only at the next boot, and if the boot-time lookup fails the unit logs that no hub address is available and keeps retrying. Each announce attempt is bounded and yields to the control loop between slices, so even a hub that accepts the connection and then stays silent does not consume the window. The 8-second window applies only to genuine hangs once the unit is running. After a watchdog reboot the unit reconnects and announces again from the boot path.
- **Scheduled soft reboot.** You can configure a daily soft reboot for memory hygiene via the `reboot` key in `config.json` (disabled by default). It turns the relays off, disconnects Wi-Fi, and soft-resets at the configured hour — but unlike a watchdog or power-cycle reboot it preserves cumulative uptime.

## What survives a restart

The unit saves the choices you make, not just the wiring you flash. Three things live in the unit's own saved settings — a file separate from `config.json` — and are restored every time it boots, after **any** restart: a power cut, a soft or hard reboot, the scheduled nightly reboot, and even a watchdog-triggered restart.

| What you set | Comes back after a restart? |
|---|---|
| Target temperature and humidity | **Yes** — the values you last applied |
| Control loop on/off | **Yes** — the loop restarts as you left it |
| Hand-set fan and humidifier (loop off) | **Yes, while the loop is off** — exactly as you left them |
| Hand-set **heater** (loop off) | **Never** — it always returns **off** |

**Why the heater always comes back off** is a safety rule, not an oversight. Nothing on the unit can cool — the heater only adds heat, and the fan removes moisture — so temperature has no active cooling. While the loop is on, temperature is regulated and the heater is switched deliberately. But while the loop is **off**, nothing regulates temperature at all, so a heater that came back on would be an unattended heat source with nothing watching it. The unit therefore never restores the heater to on. You can still switch it on by hand while the unit is running; it simply never comes back on by itself after a restart.

Worth knowing:

- **A saved change is durable the moment it is applied.** The unit writes your change before it reports success, so once the dashboard or unit page shows it applied, it is stored. A power cut *during* the write leaves the previous value intact — the write is atomic, so the saved settings are never left half-written or corrupt.
- **Only your actions are saved.** The loop switching relays on its own schedule never writes to the saved settings, so what comes back after a restart is your last choice, not whatever the loop happened to be doing.
- **A batch still takes over.** After a power cut, the restored targets govern until the unit reconnects to a hub that is running a batch — at which point the batch's targets take over exactly as before.

**What to check after a restart.** Glance at the unit page or the dashboard and confirm three things: the targets are the ones you want, the loop is in the state you intend, and — if the loop is off — the fan and humidifier are where you left them. The heater being off is correct, not a fault.

## mDNS caveats

The unit can be reached at `http://<device_name>.local:5000` without knowing its IP, but only when all of these hold:

- **Firmware ≥ v1.26.0** — the mDNS fix landed in v1.25.0 stable, but v1.25.0 pre-release builds do not have it. v1.26.0 is the recommended minimum and the confirmed-working version.
- **Station (normal) mode only** — mDNS does not resolve while the unit is in offline (AP) mode; use the IP (`192.168.4.1`) there.
- **Same subnet** — mDNS is link-local. A unit on a different VLAN or subnet needs an mDNS reflector on the router.

## Verify it is running

Find the Pico's IP (your router's DHCP table, or a REPL) and request:

```bash
curl http://<pico-ip>:5000/health
```

A JSON response with RAM, storage, Wi-Fi signal, and uptime means the API is up. If the request times out, check the onboard LED — a **solid** LED means Wi-Fi is connected and the unit is waiting on its first hub announcement — then re-check `wifi.ssid` and `wifi.password` in `config.json` and redeploy. The full LED reference is on the [Status indicators](/pico-units/status-indicators) page.
