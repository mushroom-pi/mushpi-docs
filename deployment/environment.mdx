The hub's server reads all of its runtime configuration from environment variables, validated at boot against a Joi schema — there is no config file to edit inside the image. In the self-hosted deployment you supply them through the `.env` file beside the compose file, which Compose passes into the container's environment; you can also set them as ordinary container environment.

The table below lists the key variables an operator actually touches — it is not the exhaustive list. The complete, canonical reference is **generated from the server's validation schema** and published in the server repository: [mushpi-server/docs/ENVIRONMENT.md](https://github.com/mushroom-pi/mushpi-server/blob/dev/docs/ENVIRONMENT.md). It is regenerated with `yarn docs:env` in `mushpi-server`, so it always reflects the schema.

## Key variables

| Variable | Default | What it does |
|---|---|---|
| `PICO_ANNOUNCE_SECRET` | — | The shared secret Pico units send in the `X-Pico-Secret` header when they announce. **Required in production** — the server refuses to boot without it. Use the same value as `hub_secret` in every unit's `config.json`. |
| `APP_HOST` | `localhost` | Server host. Set it to the hub's LAN hostname so recipe and batch image URLs resolve on other devices. |
| `APP_PORT` | — | Server port. The published container serves the dashboard and the API together on port 3000. |
| `SQLITE_PATH` | `data/app.sqlite` | Path to the SQLite database file. Inside the published container this is `/data/app.sqlite`, under the persistent data volume. |
| `UPLOAD_DIR` | `data` | Directory where uploaded batch and recipe images are stored. |
| `LOGS_LEVEL` | `info` | Log verbosity. Allowed values: `info`, `trace`, `silent`, `debug`, `error`, `fatal`, `warn`. |
| `LOGS_PATH` | `data/logs` | Directory where log files are written. |
| `LOGS_LIFE_DAYS` | `7` | Log retention in days. |
| `READINGS_RETENTION_MONTHS` | `6` | Months of sensor readings to keep. Minimum `1`. |
| `APP_HTTPS_ENABLED` | `false` | Declares that the browser-facing deployment is reached over HTTPS (TLS terminated upstream or directly). Does **not** configure TLS in the app — it only gates the HTTPS-only security headers: Helmet HSTS and the CSP `upgrade-insecure-requests` directive. |
| `MAX_REQUESTS` / `MAX_REQUESTS_TIME` | — | Opt-in rate limiting. `MAX_REQUESTS` is the maximum number of requests per window; `MAX_REQUESTS_TIME` is the window length in milliseconds. They must be set **together** — setting only one is a configuration error and the container **refuses to boot**. See [Rate limiting](#rate-limiting). |

## Rate limiting

By default the server applies no request throttling. To enable it, set **both** `MAX_REQUESTS` (requests per window) and `MAX_REQUESTS_TIME` (window length in milliseconds) in the deployment `.env` — uncomment the pair in `.env.example`. The pair must be set **whole**: one without the other is a validation error and the server does not start.

For a LAN or Tailscale deployment, the recommended starting point is `MAX_REQUESTS=300` / `MAX_REQUESTS_TIME=60000` — about 5 requests per second per client IP.

When the limit is enabled:

- A client that exceeds the limit receives `429` responses carrying `X-RateLimit-*` headers.
- `/health` is always exempt, so the container health check is unaffected.
- The counters are **in-memory, per container** — restarting the container resets them.
- The server does not trust reverse-proxy headers: behind a proxy such as Tailscale Serve, all clients share one bucket. Leave the pair **unset** behind a proxy unless a shared budget is intended.

## A note on `docker exec`

To fix data-directory ownership the image starts as root and then drops privileges, so `docker exec <container> …` now lands as root rather than the `node` user; PID 1 still runs as `node`. Use `docker exec --user node <container> …` to run a command as the `node` user, as the image used to.

The full variable list — including `NODE_ENV`, `APP_SECRET`, `CLIENT_URL`, the Swagger docs variables and the remaining logging switches — lives in the server repository:

**[https://github.com/mushroom-pi/mushpi-server/blob/dev/docs/ENVIRONMENT.md](https://github.com/mushroom-pi/mushpi-server/blob/dev/docs/ENVIRONMENT.md)**

The file is generated from the server's Joi validation schema (`yarn docs:env`) and is the canonical list; this page intentionally covers only the operator-facing subset.

## Not server environment variables

Two variables you set in the deployment `.env` are **not** read by the server: `MUSHPI_DATA_DIR` (the host directory holding all persistent state) and `MUSHPI_IMAGE_TAG` (which image tag to pull). They are interpolation variables consumed by the compose file in the deployment repository, and are documented in [Self-hosting](/deployment/self-hosting).

## Not server settings either

The hysteresis control loop — its deadbands, the control period and the minimum output runtime — is configured in each unit's `config.json`, not through server environment variables. That behaviour is owned by the firmware and covered in [Hysteresis control](/configuration/hysteresis-control).
