Mushroom Pi ships as a single container image that bundles the NestJS backend and the React dashboard together, serving both on port 3000. You pull one image, run one container, and your grow-control hub is live — there is no build step. This page tells you what you are deploying, what you need before you start, and how to run it.

## What you are deploying

The hub is three things, and only three:

- **One image.** You pull `ghcr.io/mushroom-pi/mushpi` from GitHub Container Registry. The package is public, so the pull needs no credentials and you never build it yourself.
- **One port.** Port 3000 serves the built dashboard and the API together — production is same-origin, so there is no separate frontend to run.
- **One data directory.** All persistent state lives in one host directory that you choose: the SQLite database at `/data/app.sqlite`, plus uploaded images and logs.

The hub runs on any Docker-capable single-board computer. A Raspberry Pi 3 Model B v1.2 (1 GB) is what the maintainer tests on, so that is a known-good starting point, not a requirement.

For access from outside your local network, you set up Tailscale — a private, encrypted mesh that needs no port forwarding and no TLS certificates. The [remote-access guide](/configuration/remote-access) covers it.

## Prerequisites

### Hardware and OS

- A hub: any single-board computer (or small PC) that can run Docker on 64-bit Linux.
- **The 64-bit OS is a hard requirement.** The published image is built for `arm64` and `amd64`, so a 32-bit OS cannot pull it. If you are flashing Raspberry Pi OS, select the 64-bit image in Raspberry Pi Imager.
- **Raspberry Pi Imager 2.0.6 or newer** is required to flash and customise a current Raspberry Pi OS image — older versions fail silently. Flashing the card is its own step; the SD-card provisioning page covers it.
- **Headroom.** The tested reference board (1 GB of RAM) is the bare minimum that has been verified, not a requirement: 1 GB is enough for this stack but leaves little headroom, so avoid running other services alongside Mushroom Pi on a board that small.

### Software

- **Docker Engine with the Compose v2 plugin** — the `docker compose` subcommand (with a space).
- A user account that can talk to the Docker daemon. On Raspberry Pi OS, add yourself to the `docker` group with `sudo usermod -aG docker $USER`, then log out and back in.
- `git`, to clone the deployment repository.

No registry login is needed — the image is public, so `docker compose pull` runs anonymously. Do not put a GitHub token on the hub.

### Network

- Outbound HTTPS to `ghcr.io`, to pull the image.
- LAN access between the hub and each Pico unit: the hub polls every unit over the local network, and each unit announces itself to the hub when it boots.
- Browsers on your LAN reach the dashboard on the hub's port 3000.

## Configure the environment

The hub reads its configuration from a `.env` file beside the compose file. Copy the template and fill in the one required value:

| Variable | Required | What it sets |
|---|---|---|
| `PICO_ANNOUNCE_SECRET` | **Yes** | The shared secret Pico units send in the `X-Pico-Secret` header when they announce. The server refuses to boot without it in production. Generate one with `openssl rand -hex 32`, and use the same value as `hub_secret` in every unit's `config.json`. |
| `MUSHPI_DATA_DIR` | No | The host directory that holds all persistent state. Defaults to `./mushpi-data` beside the compose file. Point it somewhere you back up. |
| `MUSHPI_IMAGE_TAG` | No | Which image tag to pull. Defaults to `latest`. |

These are the compose interpolation variables plus the one required server variable. The server's remaining settings — `APP_HTTPS_ENABLED`, the opt-in `MAX_REQUESTS`/`MAX_REQUESTS_TIME` rate-limiting pair, `APP_HOST`, logging and reading retention — are covered in [Server environment variables](/deployment/environment).

## Run it

Clone the deployment repository and start the stack:

```bash
git clone https://github.com/mushroom-pi/mushpi-ops.git mushpi-ops
cd mushpi-ops
cp .env.example .env
```

Edit `.env` and set `PICO_ANNOUNCE_SECRET`. Then:

```bash
docker compose up -d
```

The first `up` pulls the published image and starts one container. There is nothing to build and no further setup on the host. The repository's local build toggle (`docker-compose.override.yml`) is untracked by design, so it never ships in a clone — a plain `docker compose up -d` like the one above always **pulls** the published image and never builds one.

## Verify it is up

Open a browser on any device on the same network and go to:

```
http://<hub-ip>:3000
```

Replace `<hub-ip>` with the hub's address — find it with `hostname -I` on the hub. The dashboard should load within a few seconds of the container starting.

If it does not load, check the container state:

```bash
docker compose ps
docker compose logs mushpi
```

## Validation status

This deployment path has been validated in a local build and smoke test. It has not yet been validated on the target hardware, so treat the first run on your own hub as a test.
