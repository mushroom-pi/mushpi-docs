Updating Mushroom Pi is deliberately minimal: the deployment is one container pulled from GHCR, and the update is two Compose commands. Backups are the same story — all persistent state lives in one directory on the host, so a backup is a copy of that directory.

## Update the stack

**Back up first** (next section) — then, from the `mushpi-ops` checkout on the hub — the directory that holds `docker-compose.yml`:

```bash
docker compose pull && docker compose up -d
```

`docker compose pull` fetches the newest image, and `docker compose up -d` recreates the container on it. The update is a container recreate — that is the whole mechanism. Your data is not touched: the persistent state is a host directory bind-mounted into the container, not container storage.

### Rolling back

Pin the image tag the stack pulls by setting `MUSHPI_IMAGE_TAG` in `.env` to the older release tag (for example `MUSHPI_IMAGE_TAG=v0.8.0`), then bring the stack up again:

```bash
docker compose up -d
```

By default the stack pulls `ghcr.io/mushroom-pi/mushpi:latest` — `MUSHPI_IMAGE_TAG` defaults to `latest` in `docker-compose.yml` and is documented (commented out) in `.env.example`. Removing the override and running `docker compose pull && docker compose up -d` returns you to the newest image.

## What this page does not document

The following are **not implemented today**, so they are not documented here — none of them is a step this deployment performs:

- **Image pruning** — no cleanup of old images is part of the workflow.
- **An explicit stop before pulling** — nothing stops the stack before `docker compose pull`; Compose recreates the container in one step.
- **A post-update health check** — there is no documented verification step beyond the container running.

## Back up the data directory

All persistent state lives in **one directory on the host** — whatever `MUSHPI_DATA_DIR` points at in `.env` (default `./mushpi-data` next to the compose file). That directory holds the SQLite database (`app.sqlite`), the uploaded images and the logs.

To back it up, **stop the stack, copy the directory, start the stack again**:

```bash
docker compose stop
cp -a ./mushpi-data /path/to/backup/     # or: rsync -a ./mushpi-data /path/to/backup/
docker compose start
```

Substitute your `MUSHPI_DATA_DIR` path if you set one. Copying the directory **while the stack runs is not the documented approach** — the SQLite database can be mid-write, which is exactly what stopping avoids.

## Pico firmware updates

Pico firmware updates are **USB-flash, not ops** — they are done from a computer over USB and are covered by the hardware pages, not by this deployment workflow. See [Pico firmware](/hardware/pico-firmware).
