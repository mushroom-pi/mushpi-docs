`mushpi-mock` is a FastAPI service that mirrors the full `mushpi-grow` REST API — the announce endpoint, the status polling endpoint, and the relay control endpoint — responding exactly as a real Pico 2W would. The Mushroom Pi backend cannot tell the difference between a mock unit and a real one. This means you can build new server features, test dashboard flows, and experiment with recipe logic on your laptop without owning any hardware at all.

## Prerequisites

Before you start, make sure you have the following installed:

- **Python 3.12 or later**
- **[uv](https://docs.astral.sh/uv/)** — the fast Python package and project manager used by `mushpi-mock`

## Run the Mock

<Steps>
  <Step title="Clone the mushpi-mock repository">
    ```bash
    git clone https://github.com/mushroom-pi/mushpi-mock.git && cd mushpi-mock
    ```
  </Step>

  <Step title="Install dependencies with uv">
    `uv sync` reads the project's lockfile and installs all dependencies into an isolated virtual environment in one step — no manual `pip install` or `venv` creation needed:

    ```bash
    uv sync
    ```
  </Step>

  <Step title="Start the mock service">
    Launch the `mushpi-mock` CLI through `uv` so it runs inside the managed environment:

    ```bash
    uv run mushpi-mock start
    ```

    This starts one mock unit, `mock-tent-1`, on **port 5000** and prints a confirmation once it's ready to accept requests. The Mushroom Pi server must be running on `http://localhost:3000` — the mock's default `server_url`; override it with a config file passed via `--config` if your server runs elsewhere. Each mock unit announces itself to the server on startup with `POST /v1/pico-units/announce` — the same mechanism as the real firmware.
  </Step>

  <Step title="Register the mock as a unit in the Mushroom Pi backend">
    Open the Mushroom Pi dashboard (or call the backend API directly) and add a new Pico unit pointing to:

    ```
    http://localhost:5000
    ```

    The backend polls this address immediately when the unit is created (and again on its 60-second cycle), so the mock unit appears as active in the dashboard right away.
  </Step>

  <Step title="Develop against the mock">
    The mock responds to all standard endpoints — announce, status, and relay control — just like a real Pico. Sensor readings follow the firmware's hysteresis control loop rather than random noise (see *What the Mock Simulates* below), and relay state changes are tracked in memory so control commands round-trip correctly. Work on your feature, watch the dashboard update, and iterate without touching any hardware.
  </Step>
</Steps>

## What the Mock Simulates

The mock does **not** produce random noise. It simulates the same simplified threshold-based control loop that runs on the real Pico firmware:

- **Humidity**: drifts down → when `humidity ≤ setpoint`, humidifier ON, fan OFF (chases the target upward aggressively) → when `humidity > setpoint + hyst_hum`, fan ON, humidifier OFF (corrects overshoot) → deadband between `setpoint` and `setpoint + hyst_hum` where both are OFF (natural drift). Humidifier and fan are mutually exclusive.
- **Temperature**: drifts down → when `temperature ≤ setpoint`, heater ON → when `temperature > setpoint`, heater OFF. No explicit hysteresis band — thermal lag in the drift rates produces natural oscillation around the setpoint.

This produces the characteristic sawtooth oscillation that makes dashboards and charts look realistic and meaningful. Relay states are tracked in memory for every unit, and the REST API surface mirrors `mushpi-grow/spec/openapi.yaml` exactly, so the server uses the same code paths for mock and real units.

## CLI Flags and Multiple Units

Every option of the `start` command is available as a CLI flag; a flag overrides the config-file value when both are given.

| Flag | Purpose |
|---|---|
| `--count` / `-n` | How many mock units to run (default: one `mock-tent-1` on port 5000) |
| `--handles` / `-H` | Comma-separated unit handles, e.g. `grow-left,grow-center,grow-right` |
| `--base-port` / `-p` | Port for the first unit; additional units take the consecutive ports |
| `--seed-days` | Days of backdated readings to seed on startup (requires `--db-path`) |
| `--db-path` / `-d` | Path to the server's SQLite database — required for `--seed-days` |
| `--announce-ip` | IPv4 announced as the unit's `ip` (default: `127.0.0.1`) |
| `--config` / `-c` | Path to a config JSON file overriding the defaults |

To simulate a multi-unit grow operation, start several units in one command:

```bash
# Three units with custom handles
uv run mushpi-mock start --count 3 --handles grow-left,grow-center,grow-right
```

Each unit takes the consecutive port after `--base-port` (default 5000), announces itself to the server, and appears as its own unit — register each address in the dashboard and you have a fully simulated multi-chamber environment to develop against.

## Backdated Seeding

For instant demo readiness, `--seed-days` populates the server's database with days or weeks of historical readings, written directly to the server's SQLite database — so charts show history the moment you open the dashboard:

```bash
# Seed 14 days of backdated data for three units
uv run mushpi-mock start --count 3 --seed-days 14 --db-path /path/to/app.sqlite
```

Seeding requires `--db-path` pointing at the server's SQLite file — on a self-hosted hub it lives in the bind-mounted data directory as `app.sqlite`.

```
mushpi-mock/
├── pyproject.toml        # Dependencies, scripts, build config
├── uv.lock               # Lockfile (like yarn.lock)
├── config.example.json   # Example config with defaults
├── README.md             # Standalone usage guide
├── LICENSE               # MIT
├── .python-version       # Python version pin
├── scripts/
│   └── check-version-alignment.sh  # grow ⇔ mock version check (run manually)
└── src/mushpi_mock/
    ├── __init__.py       # Package docstring + the mock's own __version__
    ├── VERSION           # Represented firmware version (must match grow)
    ├── main.py           # FastAPI app factory + click CLI
    ├── config.py         # Pydantic config models
    ├── state.py          # In-memory unit state
    ├── router.py         # All Pico API endpoints + mock-only GET /version
    ├── simulation.py     # Hysteresis control-loop sensor data generator
    ├── seed.py           # Direct SQLite bulk seeding for --seed-days
    └── announce.py       # Server announce + retry logic
```

## Version Alignment

The mock carries **two represented versions plus its own**, and the represented ones must always match the firmware they represent:

| Version identity | Lives in | Must match | Surfaces in |
|---|---|---|---|
| Represented firmware version | `src/mushpi_mock/VERSION` + `state.py::_SOFTWARE_VERSION` | `mushpi-grow/app/state.py::_SOFTWARE_VERSION` | `GET /system`, `GET /`, the announce payload |
| Represented API contract version | `state.py::_API_VERSION` | `mushpi-grow/app/state.py::_API_VERSION` | `GET /`'s `api_version` key, the announce payload |
| The mock's own service version | `pyproject.toml` `version` | nothing — independent SemVer | mock-only `GET /version` (`mock_version`) |

The server displays the reported version, so a mock that drifted from the firmware it represents would silently mask a real incompatibility — when `mushpi-grow` bumps its firmware version or its Pico↔Server API contract version, the mock's `VERSION` file and `state.py` constants are updated in the same pass. Check alignment at any time with:

```bash
./scripts/check-version-alignment.sh
```

`GET /version` is a mock-only route — not part of the mirrored Pico API — and returns all three versions: `mock_version`, `represented_firmware_version`, and `represented_api_version`.

<Note>
`mushpi-mock` is a development and testing tool only — it does not interface with any GPIO pins, relays, or sensors. Running it in a production deployment alongside real Pico units is harmless but pointless; it will never control real hardware.
</Note>
